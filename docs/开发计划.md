# ournotes-auto 开发计划

> 2026-09-29 制定。随进度更新，已完成的项打 ✅。

## 目标

1. **能放心挂机**：自由演出连续打歌不需要人管，出错能自己恢复，MISS 率尽量接近 0。
2. **图形界面**：接入 MaaFramework 通用 UI，不再只能用命令行。
3. **功能模块化**：启动游戏、清体力、重复刷歌、全曲 AP 补完等，做成在界面里可勾选、可组合的任务。之后再加上一整套日常（领任务奖励、收获等，见阶段 7）。
4. **可以公开发布**：打包内置运行时，下载即用；保留风险声明。

已定的取舍：

- 通用 UI 以 **MFAAvalonia** 为主，同时兼容 **MXU**。两者读取同一份 `interface.json`（PI v2），参考 M9A 的做法两个一起发布。用户 2026-09-29 确认 MXU 体验也不错，两个都要正式支持。
- AP 补完覆盖 EXPERT / HARD / NORMAL / EASY 全部难度。
- 清体力时打哪些歌做成选项：当前曲 / 随机 / 指定列表 / 优先未 AP。
- 歌曲测试放在后台跑，不阻塞开发。我在开发间隙查看结果并做验收。

## 目标架构

```
interface.json               PI v2 声明：控制器、资源、任务、选项
tasks/*.json                 界面上的任务与选项（被 interface.json import）
resource/pipeline/*.json     每个任务一个入口节点 → Custom 动作 OurNotesRun；OurNotesParam.attach 存放选项值
agent/main.py                启动 AgentServer（ournotes_auto/agent/）
ournotes_auto/
  agent/                     界面选项 → 命令行参数；启动演奏子进程并转发日志、停止信号
  charts/ planner.py player/ device/   打歌核心（基本不动）
  nav/                       界面识别与操作（要扩展：指定选曲、AP 状态、LB 数量）
  tasks/                     新增：可组合的任务
    base.py                  TaskContext（配置、设备、导航、演奏会话、停止信号、进度汇报）
    start_game.py            启动游戏 → 主界面
    song_source.py           选曲策略：current / random / list / not_ap
    play_loop.py             通用连打 = 选曲策略 × 结束条件（局数 / LB 用完 / 全部 AP）
    clear_lb.py              清体力 = play_loop(结束条件 = LB 用完)
    ap_complete.py           AP 补完 = play_loop(选曲 = 未 AP，结束条件 = 全部 AP 或达到上限)
  cli.py / commands.py       命令行（演奏子进程也走这里）
tools/install.py             组装界面运行目录 install/mfaa、install/mxu（开发模式联接项目；发布模式带嵌入式 Python）
```

要点：

- **UI 与 Agent 的分工**：通用 UI 负责任务列表、选项、定时、日志和通知。真正的逻辑全部在 Python 里执行。
- **演奏放在子进程里**：Agent 进程 `import maa.agent` 后 MaaFramework 切到 Agent 模式，不能再创建自己的 Resource / Tasker（OCR 用不了）。所以 Custom 动作 `OurNotesRun` 只做参数翻译，再启动 `python -m ournotes_auto --json-log --stdin-stop --set ... run`：
  - 子进程每行输出一条 JSON 日志，Agent 按原级别转发，并按界面格式输出（MFAA 用 `info:` 等前缀，MXU 用 HTML）。
  - 界面点「停止」后 `tasker.stopping` 变真，Agent 往子进程标准输入写 `stop`，20 秒内没退出就强制结束。
  - 子进程把标准输入挪到私有句柄、0 号句柄指向 NUL：Windows 上管道有挂起的读时，加载 numpy 等扩展 DLL 会卡死。
- **设备通道**：
  - 打歌对时间精度要求高，继续用自己的 MuMu IPC 截图 + minitouch 触控。
  - MuMu 路径、实例号、adb 地址从 UI 选中的控制器推导（`controller.info` 的 MuMu extras，或 adb 路径 + 端口），用户不用再手写配置。
  - MaaFramework 自己的 ADB 控制器可能也用 minitouch：我们的 minitouch 要换成独立的文件名，只结束自己的进程，不能 `pkill -x minitouch` 误杀它的。
- **版本对齐**：MFAA 2.16.2 自带 MaaFramework 5.12.3，Agent 用 pip 的 maafw 5.14.0。`tools/install.py` 用 pip 包里的动态库替换 MFAA 自带的（官方模板也是这样替换）。

## 界面上的任务与选项（草案）

| 任务 | 选项 |
| --- | --- |
| 启动游戏 | 是否先启动 MuMu 实例；等待超时 |
| 清体力（用完 LB） | 选曲方式（当前曲 / 随机 / 指定列表 / 优先未 AP ✅）；难度；每局 LB 消耗 1~3 |
| 重复刷歌 | 曲目（当前曲 / 随机 / 优先未 AP / 指定）；难度；局数（0 = 不限）；LB 消耗 0~3 |
| 全曲 AP 补完 | 难度（多选，默认全选）；顺序（高难度优先 / 低难度优先）；每首最多尝试次数；LB 消耗 |
| 校准 | offset 校准；流速改变后的音符运动校准 |
| 全局设置 | 触控方式（minitouch / MuMu）；offset；拟人化开关与幅度；调试（连击监视、保存截图） |

安全规则继续有效，写进代码并在界面上注明：

- 不碰付费星钻。
- 「恢复LIVE BOOST」只点取消。
- 未知弹窗不点确定。

   - ✅ 换独立的二进制文件名（`ournotes_touch`，只按这个名字清理遗留进程）。
3. 🎮 长时间挂机测试（不限局数，跨过 23 点日期变更）。确认以下情况都能自动恢复：网络断开、闪退、LB 用完退回消耗 0。
   - ✅ 闪退：导航时连续 30s 认不出画面就用 `pidof` 检查游戏进程，不在了就经 adb 重新启动（和标题画面卡住共用重启次数上限，回到主界面后清零）。实机还没演练过。

   - ✅ 连击监视和演奏画面检查在各自线程里截图，MuMu 截图源整个 grab 加锁（DLL 的截图缓冲是共用的）。
   - ✅ 30 局无人值守（2026-09-29 08:54~10:20，随机 EXPERT，`--watch-combo`）：不中断，AP 29，失败 0。开头 LB 只剩 1，之后按消耗 0 继续。
     - 唯一的 MISS 3 是 Symbol II（100034）：模拟器卡了约 0.6s。连击监视 141071~141691ms 之间没截到图（平时每 100ms 一张），被漏掉的 3 个普通点击（141320 / 141523 / 141624ms）正好在这段里；执行器最大迟到只有 0.79ms，说明触控按时发出去了。

   - ✅ 标题画面的弹窗（2026-10-01，用户实际挂机时卡住）：
     - B 站 SDK 的「开启消息通知」挡住了 TAP TO START。标题画面会让导航的超时一直重新计，所以会一直卡住。现在点右上角的 ⓧ 关掉，不点「去开启」。
     - 「连接失败（发生网络连接错误）」只有一个按钮「返回标题画面」。等 10s 再点它，然后重新登录。进入游戏之前连续 3 次都连不上就报错停下。
     - 兜底：标题画面 120s 都没出现 TAP TO START，就报错停下，不再干等。
     - 实机（`start`）：关掉通知弹窗后，连续遇到 2 次「连接失败」，中间 TAP TO START 点了没反应，重启了一次游戏，最后进入主界面。
   - ✅ 首音符同步失败、演奏中生命值归零后从头重试（2026-10-01，用户提出：干等歌曲放完几乎没分，这一局的 LB 就浪费了；「终止」也拿不到演出奖励）：
     - 先确认还在演奏画面（右上角暂停按钮的模板），再点暂停 → 「重试」。
       - 之后还有二次确认「要重试并从头开始本次演出吗？」，点按钮行右边的「重试」；它和终止确认的布局一样，标题也叫「重试」。
       - 确认弹窗一关，就重新开始同步。
     - 每局最多重试 `loop.sync_retries`（默认 2）次，用完了照旧等歌曲放完。
     - 「重试」或确认点了没反应：先取消确认，再点「继续」接着放完这首歌（不点「终止」），本局放弃。
     - 别处看到重试确认：点「取消」，回到暂停菜单，按原来的方式终止。
     - 起因（用户 v0.1.1 实际挂机日志）：in your blue eyes（100092 NORMAL，LB 3）同步残差 8.14ms，比上限 8ms 只多一点，就判了失败。
     - 生命值归零：
       - 演奏画面检查每 0.5s 截一次图，同时看暂停按钮左边的生命值条（`LIFE_BAR`）。
         - 条的亮度和生命值成正比，1000 为满：平时是绿色；超过 1000 的部分在左边叠青色；300 以下变红。
         - 生命值归零后，条一直是空的，不会再回复（自由演出不会因此中断）。
       - 生命值条连续 `play.guard_life_zero_s`（默认 1s）都是空的，就停止触控，暂停重试；次数算在 `sync_retries` 里。
       - 暂停菜单的「重试」不会恢复生命值（实机：归零后重试，分数从 0 开始，生命值还是 0）。所以要先看到条亮着，才开始看它会不会变空；归零后重试的那一局看不出来，照常打完。
       - 起因（用户实际挂机，100056 NORMAL）：首音符同步正常，前 9s（35 连）也都对。之后游戏的时间轴突然比我们的时钟慢了几十 ms，多半是游戏或模拟器卡了一下（音频或渲染）。
         - 之后所有音符的头都是 GOOD/FAST（g161 G3），42 个滑条尾全部 MISS（抬早了），生命值降到 0。
         - 执行器只在开头同步一次，之后是开环的，所以纠正不回来。
         - 同一首歌重打一次是 P480 M8，复现不了，不是谱面或同步的问题。
         - 以后可以考虑演奏中途再同步：用演奏画面检查的截图比对音符位置，修正 offset。
     - 实机（LB 0）：
       - 强制同步失败：暂停 → 重试 → 确认重试 → 重新同步；用完次数后等歌曲放完。
       - 卡在重试确认上时，下一次导航会依次取消 → 终止 → 确认终止。
       - offset +300ms 时生命值 9s 左右归零（P315 M172，归零后一直是 0）。
     - 重试不会再消耗 LB（实机：持有 2，消耗 1，开始后同步失败重试一次，打完还剩 1）。
     - 已知小问题：offset +300ms 这种全 MISS 的测试里，最后 16 个触控事件还没发完，就出现了 LIVE FINISH，2s 后报「离开了演奏画面」；这一局算失败、不记录，下一局开头的导航会离开结算页。
       - 猜测原因：最后一个长按的头 MISS 后，游戏提前结束了演奏，但执行器还要按完这个长按。没有核实。
     - ✅ 重试后首音符同步失败（重试后反复「同步失败」，次数用完只能干等歌曲放完）：
       - 原因：暂停菜单「重试」后歌曲立即从头开始（点确认后约 0.2s，演奏画面约 0.36s 后出现，再过 0.16s 100056 的首音符就进入跟踪区）。首音符一直在动，等不到画面静止，等到的已是后面的音符。
       - 改法：
         - 重试时沿用第一次静止时取的基线（`NoteTracker(baseline=...)`），不等静止直接跟踪。
         - 点完确认后只认暂停按钮、不做 OCR，快速等演奏画面出现就开始同步。
         - 推算的歌曲开始时刻几乎就是开始同步的时刻，改用 `play.sync.retry_start_delay_s`（1.5s）检查有没有跟错音符。
       - 实机（AP，100056 NORMAL）：强制同步失败后重试，重新同步成功，打完 AP。
     - 100056 NORMAL 28s 处 8 个 MISS（同一次验收）：
       - 滑条长按 long#11 在另一根手指（tap#72）抬起（27365ms）后就断了。截图 27364ms 还有按住的光，27876ms 就没了。
       - 触控计划正确，事件也按时发出，复现不了。判断为模拟器 / 游戏一侧偶发丢失按住状态，没改代码。

### 阶段 5：拟人化（可选开关，默认关闭）

1. 先实测判定窗口：PERFECT 的宽度、不标 FAST/SLOW 的范围（已知约 ±2.4ms）。
   - ✅ 判定表已找到（haneoka 的游戏数据 `options` 文档：MasterLiveJudgementTiming / MasterLiveJudgementAreaOffset，辅助等级 0）：
     - PERFECT：普通音符 ±50ms，大音符（Easy*）±67ms；上划 PERFECT 为提前 83ms / 迟到 67ms。
     - 点击类音符（普通、滑条起点）会认领 ±130ms 内、自己判定区里任何新的按下；大音符最多只提前 58ms 认领。
     - 判定区纵向覆盖整条轨道，横向在音符宽度两侧各加：普通 1.0、滑条起点 2.0、大音符 2.8、上划 3.0 个单位（全宽 24 单位）。
     - 实测（阶段 5 位置随机）：按下落在好几个点击类音符的判定区里时，不一定归离它最近的那个。长条起点认领到的手指，之后的中继也按这根手指检查。
2. 三项开关：
   - 随机 GREAT 比例。
   - 时机随机偏移，限制在 PERFECT 窗口内。
   - 触控位置在音符范围内随机偏移。
3. AP 补完 / 以 AP 为目标的任务自动关闭「随机 GREAT」，其余两项限制在不影响 PERFECT 的范围。
   - ✅ 已实现（`TouchParams` 的 `great_ratio` / `jitter_ms` / `position_jitter`，`planner.py`）。界面上是三个全局选项「拟人化：随机 GREAT / 时机偏移 / 触控位置随机」，默认都关闭：
     - 随机 GREAT（约 1% / 3% / 5%，按判定总数算）：只挑普通点击（critical 没有 GREAT 这一档），按下提前或延后 64~69ms（取 PERFECT ±50 与 GREAT ±83 的正中间，单局同步误差 ±14ms 以内仍是 GREAT）。
       - 第一版用 60~73ms，两侧只有 10ms 余量。实测单局同步误差偶尔有 15ms 上下（FAST/SLOW 一边倒，平时藏在 PERFECT ±50 里看不出来），这时一部分会变成 PERFECT 或 GOOD，所以收窄到中间。GOOD 不断连击。
       - 提前或延后按下可能被别的音符认领，所以只挑认领范围（130ms + 余量 25ms + 时机偏移）内、判定区挨着的地方没有别的音符的点击；开头 1s 不挑。
       - 离线统计几首歌：这样的点击占判定总数 15%~40%，5% 以内都凑得够。
       - 选曲方式为 AP 补完 / 优先没 AP 的歌时自动关闭；开启时 offset 自动修正不算 GREAT 的 FAST/SLOW。
     - 时机偏移（±8 / ±16ms，上限 20ms）：偏移随时间缓慢漂移（每 1.5s 一个随机值，之间线性过渡），另加每个手势最多 ±3ms 的独立抖动。
       - 相近时刻的手势偏移几乎相同，不打乱已有的先后安排；认领余量、长条终点提前松手再让出独立抖动的量。
       - 故意打成 GREAT 的点击不叠加时机偏移。
     - 触控位置随机：点击、上划、追踪、长条在音符区间内横移（两侧各留 1 个单位），上下挪动最多 2% 屏高；横滑不挪（和邻居靠已有的起点挪开规则保持距离）。
       - 按下点对附近（认领范围内）每个点击类音符的判定区，都和中心保持同样的里外关系，离边界至少 0.5 个单位。这样会被哪些音符认领和不挪时一样。
       - 起因：第一版只保证不出自己的音符。春日影 EXPERT 开了位置随机，4 局里 3 局各 1 个 MISS，都在「紧挨着的两个点击类音符同时出现」处（点击 + 长条起点、两个长条起点）。
       - 连击监视定位到 MISS 在长条的中继。推测：手指挪进旁边长条起点的判定区（两侧各宽 2 个单位），长条起点认领了这根手指，不看离谁更近；之后中继按这根手指检查，它却跟着别的音符走了。
       - 同时按住的两个长条也一样：按住的手指对另一个长条的判定区（两侧各宽 2 个单位），整条路径上都和中心保持同样的里外关系（每 10ms 采样）。起因：步拾道 EXPERT 两个长条并排走，左边的在尾部变宽成 [0,11] 再横滑，手指越过右边长条的手指，右边长条下一个中继 MISS。
     - 长条终点提前松手（同一时刻另有手势按下）时，松手点夹进终点区间（两侧留 1 个单位），移到松手点的这次移动提前 4ms 单独发。
       - 起因：起死开战 EXPERT 有 4 个长条结尾 29ms 横移 6 个单位。提前 20ms 松手时手指还在半路上，离终点区间两个多单位。开了位置随机（单开位置随机、不开时机偏移也一样），一局 1~3 个 MISS。
       - 这几个 MISS 的表现：终点一直不判，连击数停在它前一个，到 350ms 后下一次按进终点判定区时才判 MISS；后面同时按下的两个音符都连上了。推测游戏没认出这次松手。
       - 第一次修正只把松手点夹进终点区间，实机没效果（M3、M2）。推测和抬起同一批发出的移动不起作用：游戏看到的松手位置还是上一批的（没抓内核事件确认）。改成移动提前 4ms 单独发之后，三项全开 3/3 无断连，不开拟人化也还是 AP。
     - 同时按下的手势（按下时刻相差不到两倍抖动幅度）共用同一个独立抖动，保持同时按下。

验收：开启后结算里的 GREAT 比例、FAST/SLOW 分布符合设置，AP 任务不受影响。

- ✅ 实机验收（2026-09-29，MuMu 实例 1，三项全开：随机 GREAT 3%、时机偏移 ±16ms、位置随机）：
  - `run --mode list` 5 首 EXPERT（起死开战、步拾道、春日影、这是我们的生存梗概、無路矢）5/5 FC，GREAT 数都正好等于目标（26/18/18/23/18），没有 GOOD 以下，连击监视无断连。
  - `run --mode ap` 同样三项全开：日志提示「本次不故意打 GREAT」，2/2 AP（Face The Next、诗超绊 EXPERT）。
  - 起死开战 EXPERT 不开拟人化 1/1 AP，改动不影响原有行为；全部测试 359 个通过。
  - 注意：单局同步误差偏大时，故意打的 GREAT 有一部分会变成 PERFECT 或 GOOD（GOOD 不断连击）。这次 5 局没有出现。

待查的歌：暂无。

- ✅ 100026（Ave Mujica）EXPERT：之前只打过 1 局，MISS 1（连击 948）。这次 2 局都 AP，连击监视断连 0 次；触控计划和那次相同（没有需要提前按下的手势），那个 MISS 算偶发，继续观察。

已解决：

- BIG MOUTH（100053）EXPERT：以前 3 局都在连击 571~573 附近断，每局 MISS 2~4 个。
  - 原因：相邻两个音符同时同向横滑（如 [0,8]+[8,16] 同时左滑）。一局 6 对里有 3 对漏判一个；间隔 4 个单位的同向横滑、相邻的同时上滑都没失败过。
  - 推测：游戏按触点当前位置找音符，判定区比音符略宽，划向邻居的那根手指被邻居抢走了。
  - 修复：同一时刻划去的那一侧有别的音符时，起点往反方向挪一个滑动距离，划完正好落在音符中心（`play.touch.flick_neighbor_shift`，两侧都有邻居时不挪）。修复后第一局即 AP。
- 焚音打（100015）EXPERT：每局固定 8 个 BAD，都在 1:56 附近的一段「上划 → 105ms 后同一位置点击」连打里，其余 EXPERT 谱面基本都 AP。
  - 原因（对照游戏判定表，见阶段 5 第 1 项）：点击类音符会认领 130ms 内、自己判定区里的任何新按下。上划的按下不算上划本身的判定，于是被 105ms 后的点击提前认领，判 BAD；那个点击自己的手指又去认领下一个，连锁下去。
  - 修复：上划、追踪、以上划 / 追踪 / 无判定开头的滑条，按下会被之后的点击认领时，改为提前按下并按住，到原时刻再划（`planner._press_leads`，`play.touch.claim_guard_ms`，默认 25ms 余量，最多提前 75ms）。全部 171 张缓存谱面里只有 6 张、共 11 个手势受影响。
  - 修复后第一局 AP（P1777，最大迟到 2.47ms）。
